# 문제 진단표 및 연구자-AI 역할 체크리스트

## 0. 문서 목적

이 문서는 현재 시뮬레이터의 문제를 다음 두 종류로 분리한다.

1. **기술 구현 문제**: 코드 추적, 오류 수정, 테스트 자동화처럼 AI가 주도적으로 해결할 수 있는 일
2. **연구 설계 문제**: 새로운 아키텍처의 가정, 배치 정책, 비교 기준처럼 연구자의 판단과 노블티가 필요한 일

프로젝트의 목표는 기존 HBM2의 bank 인접 local PCU를 유지하면서 logic die에 추가 PCU를 배치하고, 여러 bank의 데이터가 필요한 복합 연산을 logic-die PCU에서 처리하여 메모리 I/O를 줄이는 계층형 PIM 구조를 검증하는 것이다.

> 중요한 원칙: AI는 구현과 검증을 대신할 수 있지만, 무엇을 새로운 기여로 주장할지와 그 주장을 뒷받침할 아키텍처 정책은 연구자가 결정해야 한다.

## 1. 현재 문제 진단표

| 번호 | 진단 항목 | 현재 상태와 근거 | 문제 유형 | AI가 할 수 있는 일 | 연구자가 해야 하는 일 | 완료 기준 |
|---|---|---|---|---|---|---|
| D1 | 기존 bank-side 기본 연산 | `add`, `relu`, `mul` 정확도 테스트가 통과함 | 검증 완료 항목 | 회귀 테스트 유지, 입력 크기와 자료형 확장 | 해당 연산을 local PCU에 유지할지 최종 승인 | 수정 후에도 모든 기준 테스트 통과 |
| D2 | 기존 `gemv` 연산 | 4096개 출력 비교가 모두 통과한 실행 이력이 있음 | 검증 완료 항목 | 다양한 행렬 크기와 경계 조건 테스트 추가 | `gemv`를 logic-die 후보로 삼는 연구 가정 확정 | 기준·logic-only·hybrid에서 기대 경로와 값 일치 |
| D3 | `gemv_tree` 정확도 | 다수 출력이 기준값과 불일치함. 읽기 시작 열을 `4096`으로 바꾸면 출력이 대부분 0이 되어 단순 시작 주소 문제는 아님 | 기술 구현 문제 | writeback 주소와 결과 버퍼 인덱스를 추적하고 매핑 수정 | tree reduction이 표현해야 할 수학적 연산과 타일 분할 규칙 승인 | 4096개 출력 전부 기준값과 허용 오차 내 일치 |
| D4 | partial sum 배치 | `GRFB_TO_BANK_` 이후 `row`, `col`, `bank`, `grf_id`가 최종 출력 번호에 어떻게 대응하는지 명확하지 않음 | 기술 구현 문제 + 인터페이스 정의 | 주소 생성식, burst lane, tile 순서를 표로 추출하고 코드 수정 | 논리 PCU가 bank별 partial sum을 어떤 순서와 단위로 받는지 정의 | 모든 writeback 좌표에서 유일한 `output_index` 계산 가능 |
| D5 | logic-die 경로의 실체 | 명령 분기와 일부 경로는 있으나 logic PCU 개수, 지연시간, 대역폭이 실제 자원 경쟁에 완전히 반영되지 않음 | 모델 구현 문제 | 자원 모델, 큐, 지연시간, 대역폭 제한 구현 | PCU 수, 연결망, 버퍼, 지원 연산 등 제안 아키텍처 결정 | 설정값 변화가 예상 방향으로 cycle/traffic에 반영됨 |
| D6 | HYBRID 실행 정책 | 현재는 명령 종류에 따른 정적 분기에 가까우며 동적 스케줄링 정책은 확정되지 않음 | 핵심 연구 문제 | 정책 인터페이스와 여러 휴리스틱을 구현하고 비교 자동화 | 배치 비용함수와 새로운 스케줄링/매칭 정책 제안 | 동일 워크로드에서 정책별 결과를 재현하고 우수성 설명 가능 |
| D7 | MobileNetV4 워크로드 | 블록별 3분류 초안은 있으나 실제 layer shape, tensor layout, 연산 시퀀스가 테스트 입력으로 완전히 연결되지 않음 | 공동 작업 | 모델 그래프를 workload trace로 변환하고 테스트 생성 | 사용할 MobileNetV4 변형, 입력 크기, 정밀도, 대표 블록 선정 | 선택한 모델의 전체 연산 수와 텐서 이동량이 추적 가능 |
| D8 | 데이터 이동량 측정 | 정확도와 cycle은 일부 확인 가능하지만 bank-PCU, bank-logic die, host-HBM 전송량의 분리 계측이 부족함 | 기술 구현 문제 | 경로별 byte/transaction/cycle counter 추가 | 논문에서 사용할 핵심 지표와 집계 단위 결정 | 각 계층의 이동량과 병목이 표와 로그로 출력됨 |
| D9 | 성능 비교의 공정성 | bank-only, logic-only, hybrid의 자원량과 면적/전력 제약이 아직 동등하게 정의되지 않음 | 핵심 연구 문제 | 동일 조건 실행 스크립트와 결과표 생성 | 동등 면적, 동등 PCU 수, 동등 대역폭 등 비교 원칙 결정 | 리뷰어에게 각 구성의 자원 예산을 설명할 수 있음 |
| D10 | Verilog 연계 | RTL 설치와 구현 전이며 C++ 모델과 RTL 사이의 명령·타이밍 계약이 없음 | 공동 작업 | C++ 인터페이스, trace 형식, co-simulation 연결 구현 | RTL microarchitecture와 cycle 정확도 수준 결정 | 동일 입력에 C++ 기능 모델과 RTL 결과가 일치 |
| D11 | 범용성 검증 | 현재 MobileNetV4 중심이며 다른 모델에 대한 정책 검증은 이후 단계임 | 핵심 연구 문제 | 후보 모델 trace 생성과 반복 실험 자동화 | 어떤 모델군으로 일반성을 주장할지 선정 | 최소 2~3개 상이한 연산 특성에서 정책 효과 설명 가능 |

## 2. AI와 연구자의 역할 경계

| 구분 | AI가 주도 가능한 영역 | 연구자의 노블티가 필요한 영역 |
|---|---|---|
| 코드 이해 | 호출 관계, 주소식, 데이터 배치, 명령 흐름 추적 | 어떤 구조적 한계를 연구 문제로 정의할지 판단 |
| 오류 수정 | segfault, 잘못된 인덱스, buffer layout, 테스트 실패 수정 | 기존 동작과 다른 새 동작이 설계 의도에 맞는지 승인 |
| 시뮬레이터 확장 | logic PCU 클래스, 큐, latency/BW, counter 구현 | logic PCU의 개수·연결·버퍼·연산기 구조 결정 |
| 스케줄러 | 정적/휴리스틱/탐색 기반 정책 구현 | 제안 정책의 핵심 아이디어와 비용함수 정의 |
| 워크로드 | MobileNetV4 연산 trace 생성, 테스트 입력 자동화 | 대표 모델·레이어·정밀도 선정 및 선정 근거 제시 |
| 실험 | 설정 조합 실행, 로그 수집, 표·그래프 생성 | baseline, 공정성 조건, ablation 구성 결정 |
| 결과 분석 | 속도 향상, 이동량 감소, 병목 수치 계산 | 결과가 가설을 지지하는지 해석하고 연구 주장 범위 결정 |
| 논문 자료 | 재현 명령, 표 초안, 구현 설명 정리 | novelty, contribution, 한계, 선행연구 대비 차별점 작성 |

AI가 생성한 배치 정책이나 아키텍처 아이디어는 **후보안**이다. 그것을 그대로 적용하는 것만으로는 연구 노블티가 되지 않는다. 연구자는 후보를 선택한 이유, 기존 방식과 다른 점, 예상 효과, 반증 가능한 가설을 직접 확정해야 한다.

## 3. 연구자가 먼저 확정해야 할 핵심 설계 질문

아래 항목은 코드를 더 작성하기 전에 최소한 초안이 있어야 한다.

| 우선순위 | 연구 질문 | 결정 예시 | 결정하지 않을 때 생기는 문제 |
|---|---|---|---|
| R1 | logic-die PCU가 해결할 핵심 병목은 무엇인가? | 여러 bank partial sum의 집계와 bank 간 데이터 재배치 | 단순히 PCU를 하나 더 추가한 구조로 보일 수 있음 |
| R2 | local PCU와 logic PCU의 역할 경계는 무엇인가? | local: element-wise/DW, logic: cross-bank reduction/pointwise | HYBRID 정책의 근거가 없어짐 |
| R3 | 데이터는 어디에서 언제 이동하는가? | local 결과를 bank buffer에 유지한 뒤 필요한 partial sum만 logic die로 전송 | I/O 감소량을 정확히 정의할 수 없음 |
| R4 | logic PCU의 자원 예산은 얼마인가? | PCU 수, SIMD 폭, accumulator 수, local buffer 크기 | baseline과 공정한 비교가 불가능함 |
| R5 | 배치 정책의 목적함수는 무엇인가? | 총 cycle 최소화, 이동 byte 최소화, energy-delay product 최소화 | “기가 막힌 매칭”을 수식과 알고리즘으로 재현할 수 없음 |
| R6 | 정책 입력 정보는 무엇인가? | tensor shape, bank 분포, 연산량, transfer cost, queue 상태 | 하드웨어가 실제로 실행할 수 없는 oracle 정책이 될 수 있음 |
| R7 | 논문의 핵심 가설은 무엇인가? | cross-bank reduction을 logic die에서 수행하면 bank-side-only보다 HBM 내부 이동과 지연이 감소한다 | 실험 결과를 판단할 명확한 성공 기준이 없음 |

## 4. AI가 바로 진행할 수 있는 기술 체크리스트

- [x] `gemv_tree`의 명령 생성부터 `GRFB_TO_BANK_` writeback까지 호출 흐름을 확정한다.
- [x] `(channel, rank, bank, row, col, burst lane, tile)`과 `output_index`의 기존 대응 규칙을 복구한다.
- [ ] 작은 행렬 크기의 결정적 입력을 추가하여 손으로 계산 가능한 golden result와 비교한다.
- [x] partial sum이 생성, 저장, 읽기, 최종 reduction되는 각 단계의 값을 분리 출력한다.
- [x] 잘못된 PIM 모드 전환과 결과 읽기 주소를 수정하고 `gemv_tree` 전체 정확도를 회복한다.
- [x] bank-only 기존 정확도 테스트 5종을 함께 실행하여 회귀 여부를 확인한다.
- [x] logic-only와 hybrid에서 logic 명령 수, compute cycle, transfer byte/cycle, service cycle을 출력한다.
- [x] `NUM_LOGIC_PIM_UNITS`, `LOGIC_PIM_LATENCY`, `LOGIC_PIM_BW`를 rank busy time과 read 반환 지연에 반영한다.
- [x] MobileNetV4 Conv-S UIB layer shape를 입력으로 받는 manifest parser와 workload lowering 테스트를 만든다.
- [x] MobileNetV4 3x3 depthwise를 기존 bank-side MUL+ADD로 lowering하고 전체 FP16 결과를 검증한다.
- [ ] 동일 설정으로 재실행 가능한 스크립트와 결과 CSV를 생성한다.

## 5. 연구자가 수행해야 할 노블티 체크리스트

- [ ] 제안 구조가 해결하려는 기존 HBM2-PIM의 한계를 한 문장으로 정의한다.
- [ ] logic-die PCU 추가가 단순 자원 증가가 아니라 구조적 개선인 이유를 설명한다.
- [ ] local PCU와 logic PCU 사이의 연산 분할 원칙을 수식 또는 알고리즘으로 정의한다.
- [ ] cross-bank 연산의 데이터 흐름과 partial-sum 소유권을 결정한다.
- [ ] 정적 매핑, 비용 기반 매핑, 동적 매핑 중 제안 정책의 범위를 결정한다.
- [ ] baseline과 제안 구조의 자원 예산을 공정하게 맞추는 규칙을 결정한다.
- [ ] 성능, 데이터 이동량, 에너지, 면적 중 주평가 지표와 보조 지표를 결정한다.
- [ ] MobileNetV4에서 대표성을 갖는 블록과 입력 크기를 선정하고 이유를 기록한다.
- [ ] 범용성 검증에 사용할 추가 모델군과 선정 기준을 결정한다.
- [ ] 선행연구 대비 차별점, 예상 반론, 설계 한계를 명시한다.

## 6. 공동 의사결정이 필요한 항목

다음은 연구자가 설계 의도를 제시하고 AI가 구현 가능성과 수치 근거를 제공해야 한다.

| 항목 | 연구자 입력 | AI 지원 | 최종 산출물 |
|---|---|---|---|
| partial-sum protocol | 누가 생성·보유·최종 누산하는지 | 현재 주소 체계에 맞는 구현안과 테스트 | protocol 명세와 검증 코드 |
| logic PCU 구조 | 연산기, 버퍼, 병렬도 가정 | cycle/resource 모델 구현 | 구성도와 설정 파라미터 |
| 배치 정책 | 연구 가설과 목적함수 | 정책 후보 구현 및 sweep | 제안 알고리즘과 ablation |
| 비교 실험 | baseline과 공정성 원칙 | 자동 실행·통계·시각화 | 재현 가능한 실험 보고서 |
| RTL 연계 | cycle 정확도와 인터페이스 수준 | trace/co-simulation adapter | C++-RTL 검증 환경 |

## 7. 권장 진행 순서와 통과 조건

| 단계 | 담당 | 수행 내용 | 다음 단계 통과 조건 |
|---|---|---|---|
| 1 | AI | `gemv_tree` 주소·타일·lane 매핑 오류 진단 및 수정 | 정확도 전부 통과, bank-only 회귀 없음 |
| 2 | 연구자 | 핵심 가설, 역할 경계, partial-sum protocol 확정 | 1페이지 아키텍처 명세 작성 |
| 3 | 공동 | logic PCU 기능 모델과 경로별 계측 구현 | logic-only 결과가 수학적으로 정확함 |
| 4 | 연구자 | 자원 예산과 baseline 공정성 확정 | 비교표의 모든 자원 항목 정의 |
| 5 | 공동 | MobileNetV4 블록별 bank-only/logic-only/hybrid 실험 | cycle과 이동량을 블록별 비교 가능 |
| 6 | 연구자 | 새로운 매핑 정책 확정 | 알고리즘, 입력, 목적함수, 복잡도 명시 |
| 7 | AI | 정책 구현, parameter sweep, ablation 자동화 | 결과 재현 스크립트와 원시 데이터 생성 |
| 8 | 공동 | RTL 모델 및 C++ 결과 교차 검증 | 기능 결과 일치, timing 차이 설명 가능 |
| 9 | 연구자 | 추가 모델로 일반성 검증 및 논문 주장 확정 | 주장마다 대응 실험과 근거 존재 |

## 9. 현재 결론

현재 가장 먼저 해결할 기술 문제는 `gemv_tree`의 partial-sum/output 매핑이다. 이것은 연구자의 노블티 문제가 아니라 구현 정확성 문제이므로 AI가 주도해 해결할 수 있다.

그 다음부터는 logic-die PCU의 역할, 데이터 이동 protocol, 자원 예산, 배치 목적함수를 연구자가 확정해야 한다. 이 네 가지가 제안 구조의 핵심이며, 여기에서 연구의 노블티가 만들어진다. AI는 확정된 가설을 코드와 실험으로 구현하고 검증하는 역할을 맡는다.
