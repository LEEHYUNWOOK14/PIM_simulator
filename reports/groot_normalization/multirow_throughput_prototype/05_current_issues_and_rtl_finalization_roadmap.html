2. 현재 무엇이 문제인가

2.1 가장 큰 문제: 목표 주파수와 현재 주파수의 격차

기준필요/현재의미
현재 component-bound Fmax35.88MHz8-lane apply 27.87ns가 주 병목
GPU break-even85.1MHz이론적으로 GPU와 같아지는 최소치; 여유 없음
Production gate 1.3×111.1MHz모델·routing·memory 불확실성을 흡수하기 위한 최소 목표

단순한 constraint 변경으로 해결할 수 없다. 현재 27.87ns 경로를 9ns 안팎으로 줄여야 하므로 FP32 multiplier/rounding stage 재분할, fanout 제어, physical hierarchy가 모두 필요하다.

2.2 Lane 확장은 16에서 실패한다

구성대표 cyclesFmaxCore time면적 하한
4 lanes / scalar41,20136.27MHz33.11µs12.13mm²
8 lanes / scalar482035.88MHz22.85µs21.52mm²
16 lanes / scalar476119.72MHz38.60µs40.37mm²

16 lanes는 8 lanes보다 cycle을 7.2%만 줄이지만 clock이 45% 낮아지고 면적이 약 88% 증가한다. 따라서 현재 library와 microarchitecture에서는 16-lane이 명백한 열위다.

2.3 Full-top physical evidence가 없다

  • 8×4 flat top은 pre-ABC에서 flip-flop 301,301개까지 전개됐다.
  • 정규 ABC mapping은 15분 timeout, 관측 메모리 약 60%에서 종료됐다.
  • full-top mapped netlist, 통합 STA, placement, routing, congestion 결과가 없다.
  • 현재 21.52mm²와 35.88MHz는 component 합산/최대 지연 기반의 낙관적 하한이다.

2.4 Traffic 구조가 GPU보다 가볍지 않다

ArchitectureLogical traffic구성
GPU86,212,608Bactivation read + output write + affine
Hierarchical PIM prototype130,969,088Breduction read + replay/apply read + output write + affine + statistics

Normalization을 단독 offload하면 activation을 reduction과 apply에서 두 번 읽어야 한다. 연산기를 빨리 만들어도 replay traffic이 남기 때문에, 인접 연산과 fusion하지 않으면 구조적 이득이 제한된다.

2.5 검증 입력과 production 환경의 차이

  • 현재 trace 분류는 PRETRAINED_ACTION_HEAD_SYNTHETIC_BOUNDARY_INPUT이다. pretrained model code에서 얻었지만 실제 robot sensor distribution 전체를 대표하지 않는다.
  • actual BF16 live activation, 다양한 batch/sequence, training 또는 calibration corner는 추가 확보가 필요하다.
  • power/activity, thermal, voltage corners, IR drop, clock tree, CDC/RDC, DFT 결과가 없다.
  • 현재 정확도는 PyTorch normalization 수치 보존이며 모델의 task-level 성공률 향상을 의미하지 않는다.

2.6 Production memory/control RTL이 아직 없다

현재 prototype은 독립 reduce/apply stream을 testbench가 공급한다. 실제 bank command, replay address generation, DRAM write-back, bank conflict, ECC, timeout/recovery, CSR, interrupt, coherency는 구현 범위 밖이었다. 성능 gate 전에는 의도적으로 구현하지 않았다.

4. RTL 최종 확정까지 수행할 작업

Phase A — 요구사항·승격 조건 재고정선행 필수
  1. 최종 공정, library, voltage/temperature corner, 면적·전력 budget 확정
  2. 목표를 GPU 동률이 아닌 actual traffic 포함 최소 1.3×로 고정
  3. 8-lane/4-scalar/2-context를 baseline으로 동결하고 16-lane 폐기
  4. memory port 수, bank bandwidth, replay 동시성, affine cache 정책 명문화

Exit: 111MHz 목표와 memory assumptions가 architecture contract에 서명됨.

Phase B — FP32 핵심 연산기 재설계최우선 RTL
  1. fp32_mul_pipe4의 exponent/normalization/rounding을 5~6 stage로 분할
  2. FP32 add/mul valid·enable fanout을 local stage 단위로 제한
  3. apply FIFO를 flop array가 아닌 SRAM/register-file macro 친화 구조로 변경
  4. 8-lane apply와 reducer를 bank tile 단위로 합성해 9ns 수준을 목표로 반복 최적화
  5. 변경마다 20,225 primitive vectors와 6-profile bit-exact 회귀 수행

Exit: reducer/apply/scalar 모든 tile이 target corner에서 ≤9ns 또는 full-top 111MHz 달성 가능성이 입증됨.

Phase C — Hierarchical physical implementation필수
  1. 16-bank flat synthesis를 중단하고 bank tile, scalar island, global tree hierarchy 유지
  2. bank tile 1개를 P&R한 뒤 16개 replication과 broadcast tree를 별도 구현
  3. config/ready/tag 신호에 register slice와 balanced fanout tree 삽입
  4. multi-corner STA, setup/hold, clock tree, congestion, utilization 측정
  5. area 및 timing 결과를 component-sum 추정치와 교체

Exit: full-top routed netlist에서 목표 clock closure, congestion/hold violation 0.

Phase D — 실제 workload·메모리 결합 검증Gate
  1. 실제 GR00T BF16 activation을 여러 episode/seed에서 추가 capture
  2. bank mapping, row-buffer hit, conflict, replay read, output write를 transaction trace로 변환
  3. memory controller 없이 가능한 상한과 controller 포함 실제치를 분리 측정
  4. 인접 affine/attention/DiT 연산과 fusion 후보를 비교해 activation 재읽기 제거 여부 평가
  5. GPU benchmark를 같은 batch, synchronization, warm-up 조건으로 재측정

Exit: measured/trace-calibrated end-to-end speedup ≥1.3×. 미달이면 project NO-GO 유지.

Phase E — Production replay/write-back RTLPhase D 통과 후에만
  1. bank command sequencer, replay address generator, write-back queue 구현
  2. bank conflict와 read/write turnaround scheduler 구현
  3. ECC/parity, error response, timeout, cancellation, reset recovery 구현
  4. CSR/status/performance counter 및 firmware-visible contract 구현
  5. backpressure와 partial failure에서 데이터 atomicity 검증

Exit: memory-aware RTL simulation에서 loss/duplicate 0, protocol assertions 전부 PASS.

Phase F — RTL freeze verification최종 확정
  1. lint, CDC/RDC, X-propagation, reset, formal handshake/property 검증
  2. randomized tag/order/stall/bank-skew와 NaN/Inf/subnormal 회귀
  3. 6-profile full tensor 및 추가 live traces bit-exact 회귀
  4. gate-level SDF simulation, power/activity 기반 energy 분석
  5. DFT/scan, synthesis constraints, waiver, versioned manifest 확정

Exit: 아래 RTL freeze checklist가 전부 PASS되고 evidence 경로가 고정됨.

6. 권장 다음 작업 순서

  1. 즉시: 8-lane apply FP32 multiplier를 5~6 stage로 재분할하고 bank tile 9ns 목표를 검증한다.
  2. 다음: bank tile hierarchy를 유지하는 full-top synthesis/P&R flow를 만든다.
  3. 그 다음: 실제 activation 및 memory transaction trace로 1.3× gate를 다시 계산한다.
  4. 조건부: 1.3×를 넘을 때만 replay/write-back production RTL을 구현한다.
  5. 마지막: formal/CDC/gate-level/power closure 후 RTL을 최종 확정한다.
최종 한 줄 판단 지금 확정할 수 있는 것은 mixed-precision 수치 contract와 8-lane/4-scalar prototype 방향까지다. 최종 production RTL은 아직 확정할 수 없으며, 111MHz full-top closure와 actual-traffic 1.3×를 먼저 증명해야 한다.
