로직 다이 모델링·배치·연산·향후 계획

이 절은 이번 프로젝트에서 로직 다이를 어떤 원리로 표현했고, HBM 안의 어디에 둔 것으로 가정했으며, 현재 실제로 어디까지 계산했는지를 한 흐름으로 정리합니다. 아래의 로직 다이는 아직 물리 배치가 끝난 칩이 아니라 C++ cycle-level 시뮬레이션 모델입니다.

1. 어떤 원리로 모델링했는가

핵심 원리는 여러 HBM channel과 bank가 함께 사용하는 유한한 중앙 자원입니다. 로직 다이에 PCU가 있다고 표시만 한 것이 아니라, 명령이 기다리는 queue, 실제 PCU 개수, 명령 처리 latency, bank와 logic die 사이의 전송 bandwidth, buffer 용량, 자원이 찼을 때의 backpressure를 시뮬레이터 시간에 반영했습니다.

모델 요소표현한 원리시뮬레이션에 미치는 영향
Global scheduler64개 channel이 하나의 logic PCU pool을 공유PCU가 사용 중이면 다음 명령이 queue에서 대기

2. 로직 다이는 어디에 놓았는가

물리 구조 가정에서는 적층된 DRAM die 아래의 base logic die에 global PCU array, scheduler, shared buffer와 누산기를 둡니다. 기존 bank 인접 local PCU는 그대로 유지합니다. 코드에서는 MultiChannelMemorySystem에 공유 자원을 한 번만 만들고, 64개 MemorySystem/Rank/PIMRank가 같은 객체를 참조하게 하여 이 배치를 표현했습니다.

중요한 구분: 현재 모델이 결정한 것은 “모든 channel 아래에서 공유되는 논리적 위치와 자원 범위”입니다. 실제 RTL의 좌표, TSV 연결 수, 배선 길이, 면적, 전력과 발열은 아직 정하지 않았으며 Verilog 합성·물리 설계 단계에서 검증해야 합니다.

현재 가장 유망한 계층형 후보는 depthwise의 9개 tap을 bank에서 먼저 합친 뒤 최종 partial만 logic die로 보내는 방식입니다. 이 후보는 bank→logic 전송량을 2,359,296 B에서 262,144 B로 88.89% 줄였고, 전체 modeled DRAM write를 220,342건에서 199,350건으로 9.53% 줄였습니다. 제한된 128-entry, 4-port accumulator 모델에서도 최종 출력 18,816개가 모두 일치했고 총 231,309 cycle로 bank 기준 235,182 cycle보다 1.65% 빨랐습니다.

4. 향후 어떻게 진행할 것인가

  1. 자원 구조 현실화 완료: accumulator를 최대 8개 bank로 나누고 port 충돌, bank별 entry와 28×28 shape의 peak 사용량까지 측정했습니다.
  2. MobileNetV4 범위 확대: 현재 한 UIB block에서 여러 해상도·channel 조합과 연속 block 실행으로 검증 범위를 넓힙니다.
  3. 배치 정책 비교: bank-local, logic-die, hybrid 배치를 같은 정확도와 자원 조건에서 비교해 어떤 연산을 어느 계층에 둘지 정량화합니다.
  4. RTL 인터페이스 확정: C++에서 검증한 PCU 수, buffer depth, link width, valid/ready, channel mask, barrier 규칙을 Verilog module parameter와 port로 옮깁니다.
  5. 합성 결과로 재보정: Verilog 합성 후 얻은 주파수·면적·전력·실제 latency를 C++ 설정에 되돌려 넣고 성능 결과를 다시 계산합니다.
  6. 범용성 검증: MobileNetV4에서 확정한 규칙을 다른 CNN 및 reduction 중심 workload에 적용해 특정 모델에만 맞춘 구조가 아닌지 확인합니다.
추가 완료 결과: 14×14×192에서 4 banks×1 port는 33,622 cycle, 8 banks×1 port는 33,138 cycle이었고 출력 37,632개가 모두 일치했습니다. 28×28×192에서도 출력 150,528개가 모두 통과했으며 peak는 총 256 entry, bank당 32 entry였습니다. 따라서 128-entry는 고정 사양이 아니라 tile 수에 따라 달라지는 값입니다.
Tile-batch 및 전체 UIB 후속 결과: 28×28을 한 tile씩 처리하면 peak를 256에서 128 entry로 줄이면서 출력 150,528개를 유지했고, cycle은 63,910에서 65,250으로 2.10% 증가했습니다. 동일 설정의 전체 UIB에서 8 banks×1 port 후보는 230,075 cycle로 bank-depthwise 기준 233,365 cycle보다 1.41% 빨랐고, write는 225,460건에서 204,468건으로 9.31% 감소했습니다. 최종 출력 18,816개는 모두 일치했습니다.
Verilog 전환 시작: C++ 후보를 8-bank, bank당 16-entry, valid/ready 구조로 작성하고 2×256-bit dual-link arbiter까지 연결했습니다. Reduction buffer부터 공유 link까지 네 self-checking testbench가 Icarus Verilog 12.0에서 모두 PASS했고 최대 데이터 폭은 C++ 후보와 같은 64 B/cycle입니다. 다만 sustained bandwidth, FP16 합성, 전체 HBM 연결, 면적·주파수·전력은 아직 검증해야 합니다.
RTL stress 후속 검증: 512-cycle 포화 트래픽에서 1,024개의 32 B burst를 전송해 64 B/cycle을 지속했습니다. 2,000-cycle random valid/ready에서는 1,052 burst와 모든 source의 진행을 확인했습니다. 이 과정에서 stall 중 새 source가 들어오면 output이 바뀌는 결함을 발견해 grant와 payload를 hold register에 고정하도록 수정했으며 전체 RTL 회귀가 다시 PASS했습니다.
64채널 범위 정정: 초기 RTL 통합 경로는 한 rank의 8개 PIM block만 표현했습니다. 새 top-level은 64개 channel 각각의 8→1 local arbiter와 base logic die의 64→2 global arbiter를 연결합니다. 축소 기능 test와 실제 64채널 기본 parameter elaboration이 PASS했습니다. Accumulator data array도 4 KiB가 stack 전체가 아니라 rank당 값이므로 64채널 전체 하한은 256 KiB입니다.
실제 MobileNetV4 trace replay: C++에서 14×14×192 depthwise의 bank-local flush 8,192개를 cycle·channel·PIM-block별로 기록했습니다. C++ 2단계 arbitration과 64채널 RTL이 모두 정확히 4,096개의 dual-lane full cycle로 drain했고 partial·idle cycle은 0이었습니다. 따라서 이 workload에서는 64 B/cycle이 최대폭뿐 아니라 실제 trace의 sustained bandwidth와도 일치합니다.
현재 단계의 결론: “로직 다이를 추가하면 무조건 빨라진다”가 아니라, bank에서 끝낼 수 있는 연산은 가까이서 처리하고 여러 bank·channel의 결과를 모아야 하는 연산만 base logic die로 보내야 데이터 이동 감소가 성능 향상으로 이어집니다.
공유 연산기 최신 결과: 8개 source가 16-lane FP16 누산 파이프라인을 공유하는 RTL을 만들고 파이프라인 1·2·4개를 비교했습니다. 실제 MobileNetV4 64채널 trace에서는 세 후보 모두 24,576개의 부분합을 8,192개의 최종 결과로 만들었고 전체 배출 시간은 13,879 cycle로 같았습니다. 64 B/cycle link는 32 B 파이프라인 두 개로 채울 수 있어, 파이프라인 2개가 현재 면적과 처리량 사이의 우선 후보입니다.

오늘 추가한 Logic-die 누산 프로토타입

기존 depthwise는 9번의 MUL과 8번의 ADD를 bank-side에서 처리하면서 중간값을 DRAM에 반복 기록합니다. 새 경로는 bank PCU가 각 tap의 곱셈 결과만 만들고, base logic die의 공유 누산 버퍼가 같은 출력 주소의 9개 부분합을 모은 뒤 최종값만 DRAM에 기록하도록 모델링했습니다.

오류 해결: 초기에는 중간 writeback 패킷을 없앨 때 CRF의 PC/NOP 진행도 함께 사라져 odd-bank 입력 FILL이 건너뛰었습니다. Accumulator-direct 패킷이 DRAM에는 쓰지 않되 CRF context를 진행하도록 수정해 corner, edge, center를 포함한 전체 정확도를 복구했습니다.

전체 UIB에서 modeled DRAM write는 220,342건에서 199,350건으로 9.53% 감소했습니다. 64 B/cycle 직렬 전송은 265,022 cycle로 느렸고, bank MUL과 전송을 겹치면 256,484 cycle로 개선됐습니다. Link를 256 B/cycle로 높인 overlap 후보는 231,650 cycle로 기준 235,182 cycle보다 1.50% 빨라져 최초 성능 crossover를 달성했습니다.

확정 사양은 아닙니다: 256 B/cycle은 2,048-bit/cycle에 해당하므로 배선, TSV, 주파수, 면적과 전력 비용을 RTL 합성으로 검증해야 합니다. 더 현실적인 다음 후보는 128 B/cycle link를 유지하면서 bank-side에서 여러 tap partial을 먼저 합쳐 전송량 자체를 줄이는 구조입니다.

Bank-local aggregation 후속 결과

후속 구현에서는 depthwise tap을 logic die로 모두 보내지 않고 bank PCU가 먼저 합치도록 했습니다. 128 B/cycle·3-tap 후보는 231,727 cycle, 64 B/cycle·9-tap 후보는 231,178 cycle을 기록했습니다. 최종 후보는 기준보다 1.70% 빠르고, modeled write를 9.53% 줄이며, bank→logic partial 전송량을 2,359,296 B에서 262,144 B로 88.89% 줄였습니다.

계층형 배치 판단: Depthwise tap은 같은 channel과 bank 안에서 끝낼 수 있으므로 bank-local PCU가 누산하고 최종값만 logic die로 넘기는 편이 좋습니다. Logic die는 이후 여러 bank/channel을 연결하는 project pointwise와 tensor 경계·공유 buffer 관리를 담당합니다. 즉 두 PCU 중 하나를 없애는 것이 아니라 연산의 지역성에 따라 역할을 나누는 구조입니다.

유한 자원으로 현실화한 후보

무제한 C++ buffer 가정을 제거하고 rank당 128 entries, 4 update ports, latency 1로 제한했습니다. 실측 peak는 정확히 128 entries였고 전체 UIB는 231,309 cycle, 최종 출력 18,816개 PASS, modeled write 199,350건을 유지했습니다. 기준보다 1.65% 빠르며 data array 하한은 rank당 약 4 KiB입니다.

Signed fractional FP16 입력도 추가 검증했습니다. Factor 1과 factor 9 모두 software FP16 golden 128개와 정확히 일치했고 FP32 기준 최대 절대오차는 0.00601459로 같았습니다. 현재 구조는 tap 순서를 유지하므로 aggregation이 rounding 순서를 바꾸지 않습니다.

공유 FP16 pipeline과 실제 64채널 trace

누산기 하나를 source마다 복제하면 면적이 커지므로, 한 channel의 8개 source가 제한된 수의 FP16 pipeline을 round-robin으로 공유하도록 RTL을 확장했습니다. 각 pipeline은 한 cycle에 32 B, 즉 FP16 16개를 처리합니다. 따라서 64 B/cycle link를 모두 사용하려면 최소 2개가 필요합니다.

합성 수치 해석: 위 cell 수는 Yosys generic synthesis의 구성요소 합산값입니다. ASIC 면적, GHz 또는 전력을 뜻하지 않으며, 공정 library를 사용한 합성과 물리 설계 전에는 상대적 규모 비교에만 사용해야 합니다.

먼저 알아야 할 개념

PIM은 Processing-In-Memory의 약자로, 데이터를 CPU나 GPU까지 멀리 옮긴 뒤 계산하는 대신 메모리 가까이에서 계산하는 방식입니다. 이 프로젝트는 메모리 가까운 곳도 다시 두 층으로 나눕니다.

호스트 CPU/GPU

모델 실행을 지휘하고, PIM에 명령을 보냅니다. 모든 데이터를 가져와 계산하면 외부 메모리 I/O가 커집니다.

↔

Bank-side PCU

각 HBM bank 가까이에 있는 로컬 연산기입니다. 자기 bank 안의 데이터를 빠르게 처리하는 ADD, MUL, ReLU와 로컬 depthwise에 유리합니다.

↔

Logic-die PCU

HBM 아래쪽 logic die에 놓이는 공유 연산기입니다. 여러 bank·channel의 데이터를 모으는 GEMV, reduction, 전역 누산에 사용하려는 구조입니다.

비유: bank-side PCU가 각 창고 안에서 물건을 분류하는 작업자라면, logic-die PCU는 여러 창고의 결과를 모아 조립하는 중앙 작업대입니다. 모든 일을 중앙으로 보내는 것이 아니라, 가까이서 끝낼 일은 bank에서 하고 여러 bank가 함께해야 할 일만 logic die로 보냅니다.

Logic die를 어떤 원리로 모델링했는가

현재 모델은 Verilog RTL이나 트랜지스터 회로가 아니라 DRAMSim2 기반 C++ cycle-level 모델입니다. “어떤 명령이 어디로 가고, 자원이 몇 개이며, 언제까지 바쁘고, 데이터 이동 때문에 몇 cycle을 기다리는가”를 계산합니다.

1. 연산 위치를 먼저 분리

설정값 ENABLE_BANK_SIDE_PIM, ENABLE_LOGIC_DIE_PIM, PIM_TARGET으로 bank-only, logic-only, hybrid 모드를 구분합니다. PIM 명령은 PIMKernel → MemoryController/CommandQueue → Rank → PIMRank를 지나며, 명령 종류와 태그에 따라 bank 실행 문맥 또는 logic 실행 문맥으로 라우팅됩니다.

2. 64채널 전체가 공유하는 제한된 PCU로 모델링

초기 spatial-group 모델은 채널마다 logic PCU가 복제된 것처럼 동작해 성능을 과대평가했습니다. 이후 MultiChannelMemorySystem이 하나의 LogicDieScheduler를 만들고 모든 채널·rank가 이를 공유하도록 변경했습니다. 따라서 PCU가 16개이면 64채널 각각에 16개가 있는 것이 아니라, logic die 전체에 16개가 있는 모델입니다.

compute_cycles  = ceil(사용 PIM block / 명령당 PCU) × PCU latency
transfer_cycles = ceil(명령 데이터 byte / logic 내부 bandwidth)
service_cycles  = max(compute_cycles, transfer_cycles)
completion      = queue_wait + service_cycles

연산과 내부 전송은 일부 겹칠 수 있다고 가정해 둘 중 큰 값을 서비스 시간으로 사용합니다. PCU가 모두 바쁘면 다음 명령은 scheduler queue에서 기다립니다.

3. Bank↔logic 이동 비용을 공통 시간축에 반영

계층이 바뀌는 tensor는 HIERARCHY_PIM_BW에 따라 전송 cycle을 계산합니다. FP16 tensor라면 원소당 2 byte이며, 현재 64 B/cycle 조건에서 UIB의 네 번 계층 전환은 총 225,792 B, 3,528 cycle입니다. 이 값은 통계만 세는 것이 아니라 그만큼 시뮬레이터 clock을 진행시킵니다.

4. Bank와 logic의 상태를 독립 하드웨어처럼 분리

실제 두 PCU가 동시에 존재하려면 레지스터와 제어 상태를 공유해서는 안 됩니다. 그래서 bank/logic의 GRF·SRF, CRF, program counter, jump/repeat, mode와 command frontend를 분리했습니다. 한쪽 CRF를 프로그램했을 때 다른 쪽 결과가 0으로 오염되던 문제를 이 과정에서 발견하고 수정했습니다.

5. 공유 버퍼와 명령 broadcast를 모델링

Logic die는 어디에 놓았는가

물리 개념상 HBM은 여러 DRAM die를 수직으로 쌓고, 가장 아래 base logic die가 채널 I/O와 제어를 담당합니다. 추가 PCU는 각 bank 옆에 복제하는 것이 아니라 이 base logic die의 공유 연산 영역에 놓는 것으로 가정했습니다.

물리 아키텍처 관점

기존 local PCU는 bank 가까이에 유지합니다. 새 global PCU는 logic die에 모아 여러 channel의 부분합과 tensor를 받을 수 있게 합니다. 두 계층 사이에는 channel mask, payload, valid/ready, backpressure를 가진 interconnect가 필요합니다.

시뮬레이터 코드 관점

MultiChannelMemorySystem에 scheduler, weight buffer, output buffer를 각각 하나만 생성해 64개 MemorySystem/Rank/PIMRank가 공유합니다. 이것이 “logic die 전체에 하나의 공유 자원”이라는 배치를 코드로 표현한 부분입니다.

아직 하지 않은 것: logic die의 실제 좌표, 배선 길이, TSV 배치, clock tree, 열 분포, 면적은 아직 모델링하지 않았습니다. 현재는 구조적 위치와 공유 범위, 시간·대역폭·queue 제약을 표현한 단계입니다.

진행 과정

1단계 · 기존 시뮬레이터 이해와 기준선 확보

설정 파일, 64채널 전제, PIMKernel/PIMRank/CommandQueue 경로를 분석하고 ADD, MUL, ReLU, GEMV, GEMV_TREE 정확도를 검증했습니다.

2단계 · MobileNetV4 연산표와 bank/logic 배치

UIB의 pointwise, depthwise, residual을 분해하고 local elementwise는 bank-side, cross-bank MAC/GEMV는 logic-die 후보로 분류했습니다.

3단계 · Logic-die 자원 모델 연결

PCU 수, latency, 내부 bandwidth가 실제 queue와 completion cycle에 영향을 주도록 연결하고 계층 tensor 전송 비용을 공통 clock에 반영했습니다.

4단계 · 실제 UIB와 공간 병렬성

14×14×96 실제 shape, compact channel mapping, spatial wave scheduler를 구현해 최종 출력 18,816개를 검증했습니다.

5단계 · 공유 Logic die 현실화

global PCU scheduler, command coalescing, weight buffer, finite broadcast queue, backpressure를 추가해 64채널이 하나의 logic 자원을 경쟁하도록 만들었습니다.

6단계 · 독립 실행 문맥과 출력 경로

bank/logic CRF·register·mode를 분리하고, logic output이 일반 DRAM row 상태에 종속되어 생긴 교착을 독립 output frontend로 수정했습니다.

7단계 · 전 채널 병목 계측

mode, bank state, timing, epoch, barrier, write bus를 any/all-active로 분해하고 잘못된 PRECHARGE 통계를 정정해 depthwise writeback을 다음 설계 대상으로 확정했습니다.

향후 어떻게 진행할 것인가

계층형 depthwise 누산, 유한 banked accumulator, 64채널 link, 공유 FP16 pipeline의 기능 검증까지 완료했습니다. 다음 목표는 분리해서 검증한 expand pointwise·depthwise·project 경로를 하나의 연속 RTL/C++ trace로 묶고, 공정 library 합성값으로 C++ 자원과 지연 파라미터를 보정하는 것입니다.

검증 계획

  1. 현재 통과한 bank-only와 계층형 경로를 회귀 기준선으로 고정합니다.
  2. 실제 MobileNetV4 UIB의 expand·depthwise·project 요청을 하나의 시간순 trace로 기록합니다.
  3. 통합 trace를 C++ replay와 RTL에서 각각 실행해 출력값, 요청 순서와 완료 cycle을 비교합니다.
  4. Pipeline 2개 후보에서 queue depth, accumulator entry, link stall을 함께 sweep합니다.
  5. 공정 library 합성 후 latency와 bandwidth를 C++ 설정에 되돌려 넣어 end-to-end 결과를 다시 계산합니다.

  • Logic-die 핵심 reduction·arbiter·FP16 pipeline은 SystemVerilog로 구현했지만, 전체 HBM/모든 UIB 단계를 합친 완성 RTL은 아닙니다.
  • PCU 수와 bandwidth 후보값은 물리 합성 전 가정입니다.
  • 전력·열·TSV 배선·면적은 아직 직접 계산하지 않았습니다.
  • 현재 end-to-end 기준 workload는 MobileNetV4 UIB 한 블록입니다.
  • 일부 성능 개선은 서로 다른 자원 모델 조건이므로 같은 표의 숫자만 보고 단순 비교하면 안 됩니다.
  • 현재 가장 강한 주장은 “pointwise와 depthwise 누산을 포함한 C++ 전체 UIB가 정확하고, 실제 depthwise trace가 64채널 RTL과 FP16 bit 수준에서 일치한다”는 것입니다. 이는 최종 칩 성능이나 물리 실현 가능성의 확정을 뜻하지 않습니다.
